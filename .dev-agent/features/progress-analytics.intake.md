# Intake: Динамика прогресса

## Understood

Нужен экран прогресса поверх уже сохранённой истории тренировок: стрик, сводная статистика, динамика отдельного упражнения, личные рекорды и распределение подходов по группам мышц. Каждая новая серверная реализация репозитория должна иметь in-memory пару и реалистичные demo-данные.

## Ambiguous

Стрик можно считать по календарным дням подряд или по выполнению расписания. Согласован вариант по расписанию: дни отдыха не разрывают серию, пропущенный запланированный день разрывает.

## Facts

- FACT: История уже хранит дату, продолжительность, упражнения, подходы, повторения и вес — `lib/domain/models/workout_record.dart`, `exercise_record.dart`, `set_record.dart`.
- FACT: Расписание хранит дни недели — `lib/domain/models/training_schedule.dart` и `training_day.dart`.
- FACT: Сервер уже отдаёт полную историю и расписание; новый endpoint не требуется — `lib/data/repositories/serverpod_workout_repository.dart`, `serverpod_training_schedule_repository.dart`.
- FACT: Третий tab уже использует иконку графика и открывает историю — `lib/app/router/app_router.dart`, `lib/ui/core/widgets/app_shell.dart`.

## Questions

Нет блокирующих вопросов: продуктовый вариант согласован в предыдущем сообщении пользователя.

## Assumptions

- A1: Стрик прошлого рассчитывается по текущему расписанию — cost if wrong: изменение расписания может переинтерпретировать старую серию; для точного архива позже понадобится snapshot расписания в записи тренировки.
- A2: Расчётный максимум использует формулу Epley `weight * (1 + reps / 30)` — cost if wrong: показатель может отличаться от фактического 1ПМ, но остаётся последовательным индикатором динамики одного упражнения.
- A3: Группы мышц сравниваются по числу выполненных подходов, не по весу — cost if wrong: не отражается субъективная интенсивность, зато не смешиваются несопоставимые упражнения.

## Acceptance criteria

- AC1: Локальный запуск показывает demo-историю с несколькими неделями тренировок без backend.
- AC2: Серверная и in-memory реализации аналитики используют одну расчётную функцию.
- AC3: Экран показывает текущий и лучший стрик, тренировки, минуты и подходы за период.
- AC4: Пользователь выбирает период и упражнение, после чего график показывает 1ПМ, максимальный вес или объём.
- AC5: Экран показывает личные рекорды и подходы по группам мышц.
- AC6: Из tab прогресса можно перейти к существующей истории тренировок.
- AC7: После изменения расписания или завершения тренировки аналитика перезагружается.
- AC8: Loading, empty и error состояния имеют видимую обратную связь; error содержит повтор.

## Scope

В scope: Flutter read-модель, репозитории, fixture, экран, навигация, обновление связанных view model, unit/widget-тесты. Вне scope: миграция БД, новый Serverpod endpoint, сравнение весов разных упражнений, рекомендации тренера.

## Success metric

Пользователь может открыть tab «Прогресс» и по сохранённым тренировкам понять регулярность и изменение показателей выбранного упражнения.

## Data

Derived read-model из `TrainingSchedule` и `List<WorkoutRecord>`; новые данные не сохраняются.
