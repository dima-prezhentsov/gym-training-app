# Отчёт: аналитика прогресса

## Результат

Добавлен раздел «Прогресс», который строит статистику из расписания и истории тренировок. Одна и та же расчётная модель используется с серверными и in-memory репозиториями.

## Реализовано

- Периоды: 4 недели, 3 месяца и всё время.
- Текущий и лучший стрик по выполнению запланированных тренировочных дней.
- Количество тренировок, минут и подходов за выбранный период.
- Динамика каждого упражнения по расчётному 1ПМ (формула Epley), максимальному весу и объёму.
- Личные рекорды и распределение нагрузки по группам мышц через количество подходов.
- Встроенная история тренировок внутри третьего таба «Прогресс».
- Серверная и in-memory реализации `ProgressRepository` на общей расчётной функции.
- Отдельная in-memory реализация `TrainingOverviewRepository`.
- Демо-история на восемь недель для локальной разработки.
- Обновление аналитики после завершения тренировки и изменения расписания.
- Защита view model от устаревших ответов при быстром переключении периода.

## Архитектурные решения

| Компонент | Источник данных | Ответственность |
| --- | --- | --- |
| `ProgressRepository` | schedule + workout history | Контракт загрузки аналитики |
| `InMemoryProgressRepository` | in-memory репозитории | Локальная разработка и тесты |
| `ServerpodProgressRepository` | серверные репозитории | Аналитика по данным backend |
| `calculateProgressOverview` | доменные модели | Единые расчёты для обеих реализаций |
| `ProgressViewModel` | `ProgressRepository` | Период, метрика, упражнение и async-состояния |

Отдельный backend endpoint не добавлялся: текущие объёмы данных позволяют вычислять статистику на клиенте, не дублируя правила для local/server режимов.

## Проверки

- `dart analyze` — без замечаний.
- `flutter test` — 37 тестов прошли.
- `flutter build web --release --base-href /gym-training-app/ --dart-define=BACKEND_URL=https://gym-training-api.onrender.com/` — успешная production web-сборка.
- Проверка персональных данных и отладочного логирования в `lib/` — совпадений нет.
- Приложение вручную не запускалось на завершающем этапе: ручную проверку выполняет пользователь.

## Ограничения и следующие шаги

- Аналитика использует текущее расписание; исторические версии расписания пока не сохраняются.
- Расчёты выполняются на клиенте. При существенном росте истории понадобится серверная агрегация и пагинация.
- Стрик не считает текущий запланированный день пропущенным, пока день не завершён.
- Ручной smoke-тест в Telegram WebView остаётся за пользователем.
