# Backend, Telegram auth и постоянное хранение — спецификация

## Цель

Данные расписаний и завершённых тренировок переживают перезапуск Mini App и доступны только Telegram-пользователю, которому принадлежат.

## Границы

- Входит: Dart backend, PostgreSQL, проверка Telegram `initData`, серверная сессия, CRUD расписания, запись и чтение истории, Flutter API-репозитории и конфигурация deploy.
- Не входит: аналитика роста, социальные функции, уведомления, платежи, админка и перенос существующих in-memory данных.

## Архитектура

- Backend: Serverpod 3.4.x и PostgreSQL.
- Flutter передаёт только исходную строку `Telegram.WebApp.initData`; доверенная идентичность создаётся после HMAC-SHA-256 проверки на сервере.
- Bot token хранится только в серверных secrets/environment.
- `auth_date` ограничивает срок жизни входных данных; production не разрешает browser-заглушку.
- Серверные модели являются persistence/API-контрактом; существующие Flutter domain-модели преобразуются внутри repository-адаптеров.
- Все запросы расписания и истории фильтруются по идентификатору аутентифицированного пользователя.

## Связанность

| Что | Обновить | Почему |
|---|---|---|
| Telegram bridge | Да | Должен передавать raw `initData`, а не только display-данные |
| Запуск приложения | Да | Сначала создаётся серверная сессия, затем загружаются пользовательские данные |
| Расписание | Да | In-memory repository заменяется API-реализацией после успешной auth |
| Активная тренировка | Частично | Незавершённая сессия остаётся локальной на этом этапе |
| История | Да | Завершённые записи сохраняются и читаются через API |
| Главный demo overview | Отложено | Агрегаты будут переведены на backend вместе с аналитикой |
| GitHub Pages | Да | Нужен compile-time URL backend и обновлённая документация |
| Удаление/экспорт аккаунта | Отложено | До появления пользовательских настроек; схема сохраняет явное владение данными |

## Разбивка

Работа разделена на четыре части, каждая оставляет проект собираемым:

1. Serverpod/PostgreSQL-каркас и базовая документация.
2. Telegram auth, серверный пользователь и Flutter bootstrap.
3. Постоянное расписание и замена schedule repository.
4. Постоянная история, deploy-конфигурация и финальная проверка.

## Ключевые коммиты

1. `chore: scaffold Dart backend`
2. `feat: authenticate Telegram Mini App users`
3. `feat: persist training schedules`
4. `feat: persist workout history`
5. `chore: configure backend deployment` — только если deploy-конфигурация образует самостоятельный проверяемый блок.

## Тесты

- Серверная проверка корректной, поддельной, просроченной и неполной строки `initData`.
- Изоляция данных двух Telegram-пользователей.
- Round-trip расписания и истории через серверный contract.
- Flutter repository mapping и сохранение существующих widget-тестов с in-memory зависимостями.
- `dart analyze`, backend tests, `flutter test`, `flutter build web --release`.

## Успех

После повторного открытия Telegram Mini App тот же подтверждённый пользователь получает своё расписание и историю; поддельные данные Telegram и доступ к чужим записям отклоняются.
